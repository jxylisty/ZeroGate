# 2026-09-19 晚间复盘：ZCode 桥接签发卡死引发的 120 秒"假成功"与路由加固

> 当事渠道：zcode（start-plan 桥接，acc-big/18083、acc-fuka/18084、acc-fuka2/18086）。
> 关联文档：`01-zcode-waf-and-claim.md`（风控机制）、`03-bom-and-bridge-port-postmortem.md`（同日早间 BOM 故障）。

---

## 1. 故障表现

调用流水里成排出现：

```
zcode/glm-5.3-flash 流  zcode-fuka2  120017~120301ms  0 (0/0)  200  成功
```

- 耗时精确卡在 **120 秒整**、token 0/0、状态 200"成功"。
- 客户端体感："思考几秒 → 又思考几秒 → 断联，什么都不输出"。
- 同期 qoder 等其他渠道完全正常 → 问题锁定在 fuka2 单个桥接实例。

---

## 2. 根本原因链条（fuka2 serve.log 逐条对应）

1. **签发卡死**：22:44 起 fuka2 实例的阿里验证码求解连续 stall（XHR 单次 15-34s），
   `captcha failed after 3 attempts: solve stall / solve timeout` 反复出现，签发池抽干。
2. **请求挂满 120s 兜底**：没有签发 token 的请求挂到 zcode-proxy 自身的 120 秒超时被掐断，
   以 **HTTP 200 + 空 body** 交回（pe.js 缓存条目反复 "stalled 2x" 是卡死的伴生信号）。
3. **网关记"假成功"**：网关看到 200 干净结束的流，照常记成功、错误计数不触发 →
   **冷却/熔断永远不来**。
4. **粘性路由放大**：zcode 渠道粘性把 100% 流量压在 fuka2 一个实例上（签发池被并发抽干、
   上游频繁挑战的诱因），实例倒了以后流量继续跟进，坏了十几分钟不自愈。

> 单账号集中消耗是诱因与放大器：签发池被抽干 + 上游挑战频次上升 + 无分流兜底，三连击。

---

## 3. 当晚处置（未关闭任何进程）

- **网关侧停用 zcode-fuka2**（`POST /api/account/disable`，持久化到 state 文件），
  流量立即切到空闲健康的 acc-big / acc-fuka，实测 1.4s 恢复正常出字。
- 网关侧同时停用 zcode-cn（其桥接 18085 按方案本就不启动），
  避免故障转移撞死桥——**只在代理层不启动实例是不够的，网关层必须同步 disable**。

---

## 4. 源码加固（2026-09-19 夜改入，下次 `启动.bat` 重编译生效）

1. **零 token"假成功"熔断**（`internal/server/handler.go` 流式路径）：
   流以 200 干净结束但 **prompt/completion 全零且总时长 ≥ 1 分钟** → 按一次上游错误计账
   （`NoteError`，达阈值熔断），审计状态记 **502** 而非 200。连续 3 笔即熔断 10 分钟，
   网关自动换号；调用流水里也能直接看到失败。
2. **zcode 渠道取消长粘性，改为轮转**（`pickBridgeRotation`）：
   按「到期时间升序 + UID 稳定排序」轮转 healthy 账号——并发请求分摊到多实例
   （单账号有 start-plan 5 并发上限，集中必断），额度齐烧，快到期的优先消耗。
   其他渠道（workbuddy/traework/qoder/...）粘性行为不变。
   回归测试：`internal/server/handler_rotation_test.go`（轮转均匀性、禁用账号零流量、
   全冷却不 panic、其他渠道粘性不变）。
3. **tokens.csv 加载器逐行容错**（同日白天修）：见 `AGENTS.md` §3——加列/坏行只跳一行，
   不再"一行错全放弃"（那次症状是"关机重启数据全丢"，实为加载失败）。

## 5. 经验教训（浓缩版）

- **空流 200 ≠ 成功**：桥接/反代链路上，"200 + 零 token + 长耗时"必须当上游故障处理，
  否则熔断机制形同虚设。
- **停用账号要两层一致**：代理实例不启动 ≠ 网关不调度；`disabled` 标记才是调度层的真相。
- **单账号集中消耗是脆弱架构**：并发场景下按账号轮转分摊，既避开单账号并发上限，
  又不让一个实例的签发抖动变成全渠道断流。
- **恢复一个被停用的桥接账号**：先看实例 `serve.log` 有正常短耗时请求记录 →
  再到面板账号矩阵点"启用"；顺序反了会把流量打进刚醒的抖动实例。
- **排查入口顺序**：调用流水（120s/0 token 特征）→ 实例 `serve.log`（stall/failed 分布）
  → `data/requests.jsonl`（账号级命中率）→ 网关 `/api/state`（cooling/disabled）。
